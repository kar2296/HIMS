4. Engineering Findings — EMR-Relevant Mapping

The comparison document identifies 15 engineering findings (F01–F15). The following directly affect EMR:

F07 | P1 | React bridge does not detect nested value changes

Defect confirmed in source:


src/reactBridge.tsx:24  clonePropsSnapshot()   — shallow clone only
src/reactBridge.tsx:36  isPropsSnapshotEqual() — in-place nested mutation produces equality=true

Reproduction (from reference document): In-place obj.nested.value = 2 while prev.nested.value = 1 → bridge reports no change → React component does not re-render.

EMR Impact: Any EMR form that receives nested props (prescription detail lines, vitals, diagnoses) may fail to re-render when AngularJS scope mutates a nested object in-place. Allergy list updates inside reactProps.currentcontext.isPatientHasAllergy will not propagate if the parent object reference is unchanged.

Required fix: Replace shallow equality in isPropsSnapshotEqual with deep structural comparison (or use immutable updates in AngularJS scope before passing to React).

Source: src/reactBridge.tsx:24-67

---

F08 | P1 | Date serialisation loses one day under IST (UTC+5:30)

Defect confirmed in source:


src/react-components/DoctorPrescribeFormScreen.tsx:77  date.toISOString().slice(0,10)

Reproduction (from reference document): TZ=Asia/Kolkata; new Date(2026,8,20).toISOString().slice(0,10) → returns 2026-09-19 (one day behind).

EMR Impact: Every date field in the prescription form (PrescriptionDate, ReviewDate), and by extension in any migrated React component using toISOString().slice(0,10), will save and display one day behind when the server is in IST.

Required fix: Use local date extraction (getFullYear(), getMonth()+1, getDate()) instead of toISOString(). Verify all date conversions in DoctorPrescribeFormScreen.tsx lines 74–97 and in any new React components.

Source: src/react-components/DoctorPrescribeFormScreen.tsx:75-94

F10 | P1 | Clinical notes lack a signed-record lifecycle

Defect confirmed in source:


api/src/Server/Modules/EMR/Business/PatientClinicalNotesBo.ts:10-17
  AddPatientClinicalNotes → this.Save(req.Data)         // no status management
  UpdatePatientClinicalNotes → this.Update(req.Data)    // overwrites in place
  // No signed status check, no amendment model, no version preservation

The PatientClinicalNotes model has Rev and CreatedBy/UpdatedBy fields, but no SignedAt, SignedBy, SignedContent, AmendmentOf, or AmendmentReason columns.

EMR Impact:

- A clinician can overwrite a previously saved clinical note at any time via UpdatePatientClinicalNotes.

- No amendment trail exists — the original signed content is destroyed on update.

- DeletePatientClinicalNotes → Status=0 (soft delete) does not check whether the note is signed.

- The ConsultationBo.UpdateProgressNoteStatus method tracks a finalization state (ProgressNoteStatusId = 2) for the Consultation, but not for individual PatientClinicalNotes records.

- No comparable protection exists for DailyNote, PatientAnnotation, or other note types.

Required fix (from blueprint — F10):

1. Define draft / signed / amended / entered-in-error states for all clinical note types

2. After signing: prevent direct update; require a new amendment record linked by AmendmentOf FK

3. Preserve original signed content verbatim in an audit record

4. Block delete after signing via server-side state check

5. Include SignedAt, SignedBy columns in the model (schema migration required)

Source: api/src/Server/Modules/EMR/Business/PatientClinicalNotesBo.ts:10, api/src/Server/Modules/EMR/Model/PatientClinicalNotes.Model.ts:8

---

F11 | P1 | Concurrency control is optional in the shared update helper

Finding from reference document: "The shared update helper does contain optional Rev concurrency checks." This confirms Rev is present but concurrency checks are opt-in, not enforced by default.

EMR Impact: Two clinicians editing the same consultation note concurrently can produce a last-write-wins outcome with no conflict detection, because BaseBo.Update() does not enforce the Rev check unless the caller explicitly passes it.

Required fix: Make Rev check mandatory for all clinical record updates (Consultation, PatientClinicalNotes, PatientDiagnosis, Prescription, PatientAllergy). Test: two concurrent requests with the same Rev → second must fail with 409 Conflict.

F06 | P1 | TypeScript compile errors in frontend (EMR-adjacent)

From reference document: Exit 2 from tsc --noEmit. Diagnostics:

- 7 × TS1117 duplicate object keys

- 14 × TS2393 duplicate function implementations

- 8 × TS6133 unused declarations

EMR Impact: 7 duplicate keys in PrivilegeHelper.ts (confirmed in prior discovery) affect privilege checks for EMR screens. Build failures block CI/CD verification of any EMR React component changes.

Source: src/react-components/utils/PrivilegeHelper.ts — 435+ methods, all returning false, 7 duplicate keys.

---

F05 | P1 | Patient resource authorization not enforced

Finding from reference document: Patient record reads, exports, and file access are not gated by a role-facility-patient authorization matrix on the server.

EMR Impact: Any authenticated user can call POST /EMR/GetPatientDiagnosis with any PatientId and receive results, regardless of whether the patient belongs to their facility or the user has a clinical role.

Required fix: All EMR Get* endpoints must validate: (a) the requesting user's facility matches the patient's registered facility, (b) the user has a clinical role for that operation. This is a backend-only fix.
